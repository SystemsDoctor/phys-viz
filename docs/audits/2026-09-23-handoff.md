**Real debugging note worth reading before continuing X-49**: getting
the X-49 e2e proof right took a genuine wrong-turn detour this
session — a fragment-only URL change (`#/m/x?pj=1` vs. `#/m/x`, same
path before `#`) is a same-document browser navigation, so a second
`page.goto()` to it does NOT remount the app or re-run its
`[module]`-keyed hydrate effect; without an explicit `page.reload()`
after that second `goto()`, the test silently measures the SAME
pre-existing state twice and looks like the fix does nothing. This
cost real time to track down (added and removed several throwaway
`console.log`/probe test files along the way — all cleaned up, none
committed) before finding the actual (correct, working) root cause.
Anyone writing a projector-mode/prefs-toggle e2e test against a
DIFFERENT query string on the SAME route needs `page.reload()` after
`page.goto()`, not just a second `goto()`.

## X-49's remaining scope, glyph by glyph

Read `docs/adr/0020-line2-glyph-migration.md` and TASKS.md's X-49 entry
(both updated this session) before starting the next slice — they
record the exact pattern arrow.ts established:

- `LineMaterial({ worldUnits: false, ... })`, `Line2` (not
  `LineSegments2` directly, unless the glyph draws disconnected
  segments rather than a connected polyline).
- `material.resolution.set(info.rendererWidth, info.rendererHeight)`
  every frame, inside the glyph's existing `onFrame` callback — skipping
  this makes the line render at effectively zero width, not throw.
- `Viewport`'s projector mechanism needs no per-glyph changes; only the
  glyph's own material construction/geometry does.
- A glyph with a FIXED, small point count (a shaft, an axis) can write
  directly into the already-allocated interleaved buffer (see arrow.ts's
  `rawPositionBuffer`/`markPositionBufferDirty`) to avoid the
  per-frame allocation `LineGeometry.setPositions()` always does. A
  glyph with a VARIABLE point count (a live trace, an orbit outline)
  can't use that trick — calling `setPositions()` per frame and
  accepting the allocation is the standard three.js pattern; don't
  over-engineer around it.
- Any glyph test that filters children via `instanceof THREE.Mesh` to
  find a NON-line sibling needs to switch to an exact-constructor check
  (`c.constructor === THREE.Mesh`) — `Line2 extends LineSegments2
extends THREE.Mesh`, so the old filter silently starts matching the
  line too.
- Remaining glyphs, in the order TASKS.md's X-49 entry lists them with
  a one-line note on each: `path`, `curvedArrow`, `annotate/
dimensionLine.ts`, `axes`, `gridPlane`, `arc`, `frame`,
  `surface`'s wireframe mode (called out as possibly warranting its own
  ADR addendum — the largest remaining piece).
- Not yet investigated: the sub-audit's separate report of
  `patch.applyProps` overwriting the projector opacity floor, filed
  under the same X-49 umbrella in the original audit — confirm whether
  it's still reproducible before folding a fix into a future X-49

  glyph-slice for X-49), each with: the fix, a golden test that FAILS
