2. **X-42** (under z-up, "2D-only" shows the world x–z plane, edge-on

3. **X-38** (dark theme makes scene labels near-invisible — hardcoded
   scene background `0xeceef2`, label overlay inherits dark-mode
   `--ink-0`): **make the scene actually theme — dark theme should
   produce visible glyphs, not pin the scene to light.** Proceed
   however is most efficient; this likely means `Viewport.setTheme` (or
   equivalent) driving both the WebGL background clear color and the
   label overlay's ink color from the live theme, not just CSS. Needs
   an ADR (rendering behavior change, X-8).
4. **X-49** (projector mode's `lineWidthMultiplier` is a no-op — every
   line is `THREE.Line`/`LineBasicMaterial`, and `linewidth > 1` is
   ignored under ANGLE on Chrome/Edge/Firefox/Windows): **switch to
   `Line2`/`LineMaterial` from `three/examples/jsm/lines`** (no new
   dependency, already available via the pinned `three` package) to
   get real screen-space line width. This is scene-layer (`src/scene/
glyphs/*`), not module-layer, so it's a lower-risk, self-contained
   change relative to X-34/X-42/X-38 — every glyph that currently
   builds a `THREE.Line`/`THREE.LineSegments` (arrow shafts, `path`,
   `curvedArrow`, `dimensionLine`, `axes`, grid planes, wireframes,
   etc.) needs to move to the `Line2` API (`LineGeometry`/
   `LineSegmentsGeometry` + `LineMaterial`, which takes `linewidth` in
   world units by default but supports `worldUnits: false` for
   pixel-width — read the three.js `Line2` example before starting,
   the API differs meaningfully from `THREE.Line`). Verify visually via
   the Browser pane (Playwright, not the desktop-app browser pane,
   per this repo's `project_browser_pane_no_compositing` memory) with
   projector mode on, and re-check every existing scene glyph test

## Process notes for whoever picks this up

- One commit per X-id (or per closely-related decision-item), each
  with: the fix, a golden test that FAILS against the pre-fix code and
  PASSES against the fix (verify this explicitly — stash/copy the old
  file, rerun the new test, confirm it fails, restore), the full local
  verification sweep, a targeted Playwright run, and a TASKS.md
  `[DONE]` flip with a terse "Verified:" note (what ran, test names,
  numbers) — that's the pattern all 16 commits so far follow, read one
  or two of them (`git log --oneline`, then `git show <hash>`) to match
  the voice/format before writing the next one.
- Every `$$...$$` KaTeX block in any `explain.md` must stay on one
  line — Prettier corrupts multi-line ones (project memory:
  `project_prettier_multiline_katex_corruption`).
- The browser pane in the desktop app doesn't composite frames
  reliably — use Playwright for any rendered-frame proof, not the
  built-in browser tool (project memory:
  `project_browser_pane_no_compositing`).
- If an unrelated e2e test breaks after a fix, don't assume it's
  flaky — bisect it (this session found and fixed one genuine
  regression this way, in `tests/e2e/smoke.spec.ts`, caused by X-36
  correctly restoring native Space-on-focused-button behavior; see
  commit `ff451c9` and X-36's TASKS.md addendum for the exact method:
  a `git worktree` against the pre-session baseline commit, bisected
  forward commit by commit).
- Don't fix things opportunistically outside the current X-id's scope
  — log a new X-* entry instead (next free id is **X-61**, since X-60
  is already taken this session).
- Stop and ask the user before: any change to `src/modules/types.ts`,
  any binding palette-token change (the angular-colour ΔE proposal from
  §8 of the audit), or anything not already covered by the four
  decisions above.
